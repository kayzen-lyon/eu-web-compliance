# EN 301 549: what a web project needs beyond WCAG

Read this file when a project must meet EN 301 549 (public sector websites, services covered by the European Accessibility Act) and you need to know what the standard asks of a website in addition to the WCAG success criteria.

How this file was written:

- Every requirement below was read in EN 301 549 V4.1.1 (source `en-301-549-v411` in [sources.json](../sources.json)). Clause numbers are those of that version. No other version was read for this file, and clause numbers can differ between versions.
- The standard is under ETSI copyright. Nothing is quoted: each requirement is described in this project's words and cited by clause. Read the clause itself before relying on a detail.
- **Which version carries a legal presumption of conformity today is stated only in [regulatory-status.md](../regulatory-status.md), section 1.2.** Check it before telling a user which version they must follow. The annexes of V4.1.1 say that presumption exists only once the standard is cited in the Official Journal of the EU and only while that citation is maintained [EN 301 549 Annex ZA, Annex ZB].
- Meeting these requirements does not make a website legally compliant. It makes each requirement checkable.

Rule lines use the format of the skill: a checkbox, the requirement, and its clause in square brackets. Each rule starts with the condition under which the clause applies, because almost every clause outside clause 9 is conditional.

## 1. How clause 9 relates to WCAG

Clause 9 is the clause for web pages. Clauses 9.1 to 9.4 contain one requirement per WCAG 2.2 success criterion of level A and AA: each clause names the success criterion that the page has to satisfy and adds nothing to it.

- **Numbering rule.** The requirement for success criterion x.y.z is clause 9.x.y.z: 1.4.3 is 9.1.4.3, 2.4.7 is 9.2.4.7. The standard has no separate correspondence table. Each clause states its success criterion, and a note of clause 9.0 explains that clauses marked "Void" are inserted to keep the numbering aligned with WCAG [EN 301 549 9.0]. The rule was checked on the 55 non-void clauses; the result is in [mapping.json](mapping.json).
- **Void clauses.** A void clause is a numbering placeholder. Thirteen of the fourteen void clauses of 9.1 to 9.4 stand where WCAG 2.2 has a level AAA criterion. The fourteenth, 9.4.1.1, is void because WCAG 2.2 removed success criterion 4.1.1 Parsing [EN 301 549 9.4.1.1].
- **Level AAA.** Clause 9.5 lists the level AAA success criteria for information. It contains no requirement [EN 301 549 9.5].
- **A criterion about a feature the page does not have is satisfied.** A page with no pre-recorded video meets the captions clause [EN 301 549 9.0].
- **Pages are evaluated one by one.** A website is assessed as individual web pages, and web applications count as web pages [EN 301 549 9.0].
- **Web views inside a mobile app are not web pages.** They fall under clause 11 (non-web software), never under clause 9 and clause 11 at once [EN 301 549 9.0].
- Clause 9.0 itself is informative: it explains, it does not require.

Clause 9.0 also says that WCAG 2.2 level AA conformance is equivalent to clauses 9.1 to 9.4 together with clause 9.6 [EN 301 549 9.0]. Clause 9.7 is not part of that equivalence: a page can conform to WCAG 2.2 AA and still have clause 9.7 to check.

## 2. Requirements of clause 9 that have no success criterion number

### 2.1 Conformance requirements

Clause 9.6 makes the five WCAG 2.2 conformance requirements mandatory at level AA. They decide how the success criteria are assessed, so a list of passed criteria is not enough.

- [ ] Where the project is or includes a web page, every page meets all clauses 9.1 to 9.4, or a conforming alternate version at level AA is provided. [EN 301 549 9.6]
- [ ] Assess whole pages: conformance cannot be claimed for a page while leaving part of it out. [EN 301 549 9.6]
- [ ] When a page is one step of a process (sign-up, checkout, booking, a multi-page form), every page of the process meets the level, not only the first one. [EN 301 549 9.6]
- [ ] Rely only on uses of technologies that assistive technologies and browsers actually support. Anything provided in a way that is not supported is also available in a way that is. [EN 301 549 9.6]
- [ ] Content that is not relied upon for conformance must not prevent access to the rest of the page, and the page still conforms when that technology is turned on, turned off or unsupported. [EN 301 549 9.6]
- [ ] Four clauses apply to all the content of the page, including content not otherwise relied upon: audio control (9.1.4.2), no keyboard trap (9.2.1.2), pause, stop, hide (9.2.2.2) and three flashes or below threshold (9.2.3.1). [EN 301 549 9.6]

### 2.2 User preferences

Clause 9.7 has no WCAG equivalent.

- [ ] Where the project is or includes a web page, do not block the browser modes that present the page according to the user's preference settings, and do not explicitly override those settings for documented platform accessibility features, unless doing so is essential to the information or function of the page. [EN 301 549 9.7]

What this means in practice, from the notes of the clause: the platform of a web page is the browser; the features concerned include colour filters, contrast, text size, pointer size and text cursor; the page may still specify its own values; a CSS declaration that explicitly overrides a user setting, such as `forced-color-adjust`, is acceptable only where it is essential [EN 301 549 9.7].

- [ ] Before using `forced-color-adjust: none`, a fixed colour scheme that ignores the user's choice, or a viewport setting that disables zoom, write down why it is essential; if it is not, remove it. [best practice]

### 2.3 Live captions

Clause 9.1.2.4 (captions for live media) is a requirement of clause 9 like the others. Annex ZA leaves it out of its web table because Directive (EU) 2016/2102 does not apply to live time-based media, and says it remains necessary to make live streaming accessible [EN 301 549 Annex ZA]. The official RGAA 4.1.2 file lists no criterion for it (see `mapping.json`).

- [ ] Where a page carries live audio in synchronised media, provide live captions, even though the official RGAA 4.1.2 file has no criterion for it. [EN 301 549 9.1.2.4]

## 3. Requirements outside clause 9 that can apply to a website

Annex ZA, Table ZA.1 ("Web content") lists the clauses of the standard that relate to web content, each with the condition that triggers it. Besides clause 9 it lists clauses from 5, 6, 7, 12 and 13. Ask the question at the start of each subsection; if the answer is no, the clauses do not apply.

### 3.1 Does the site document accessibility features of its own?

Examples: a high-contrast switch, a text-size control, a simplified display mode.

- [ ] Where the site has documented accessibility features, each feature needed for a given need can be switched on without using a method that this need rules out. Illustration by this project: a contrast mode that can only be reached by reading low-contrast text would not meet this. [EN 301 549 5.2]

### 3.2 Does the site use biometrics?

Examples: sign-in by fingerprint or face through the browser, voice identification.

- [ ] Where the site uses a biological characteristic, it is never the only way to identify the user or to control the service: offer another method. [EN 301 549 5.3]

### 3.3 Does the site convert information or communication?

Examples: export of a page to another format, transcoding of video, import of documents.

- [ ] Where the site converts information or communication, keep all documented non-proprietary accessibility information, as far as the destination format can hold it. Examples chosen by this project: alternative texts, headings, captions, language. [EN 301 549 5.4]

### 3.4 Does the site have toggle controls or keyboard-level functions?

- [ ] Where the site has a control with two or three states that keeps its state (a toggle), its state can be perceived by touch or sound without operating it. For a graphical control this is normally achieved through 9.1.3.1 and 9.4.1.2: expose the state programmatically. [EN 301 549 5.6.1]
- [ ] Where the site has such a control, its state is also visible whenever the control is shown. [EN 301 549 5.6.2]
- [ ] Where a mode of operation needs simultaneous actions, such as two keys pressed together or a two-finger touch, offer a mode that does not. [EN 301 549 5.9]

Clauses 5.7 (key repeat) and 5.8 (double-strike key acceptance) are also in Table ZA.1. Their conditions concern ICT that includes a keyboard or keypad with those functions [EN 301 549 5.7, 5.8]. In this project's reading a website does not normally provide them itself; check the two clauses if the site ships an on-screen keyboard.

### 3.5 Is the site, or part of it, an authoring tool?

Examples: a CMS back office, a page builder, a rich-text editor offered to users, a form builder, a tool that publishes user-generated content.

- [ ] Where the site includes authoring tool functionality, the tool meets clauses 5.10.2 to 5.10.5 to the extent that the output format can carry the accessibility information. [EN 301 549 5.10.1]
- [ ] The tool enables and guides authors to produce content that conforms to clause 9 (web) or clause 10 (documents). Examples chosen by this project: it lets them enter an alternative text, choose a heading level, mark a table header, and prompts them to. [EN 301 549 5.10.2]
- [ ] Where the tool restructures content or converts it to another technology, accessibility information is preserved in the output if the output technology has an equivalent mechanism. [EN 301 549 5.10.3]
- [ ] Where the tool can detect that content fails a requirement of clause 9 or 10, it suggests how to repair it. [EN 301 549 5.10.4]
- [ ] Where the tool provides templates, at least one template supports the creation of conforming content and is identified as such. [EN 301 549 5.10.5]

### 3.6 Does the site play video with synchronised audio?

Clause 7 is about the player. Whether the video has captions and audio description is a matter for clauses 9.1.2.x; clause 7 asks that the player can deliver them [EN 301 549 7.1.1].

- [ ] Where the site displays video with synchronised audio, the player has a mode that displays the available captions, and lets the user choose to display closed captions. [EN 301 549 7.1.1]
- [ ] Captions are displayed in sync with their timecode; the clause sets a tolerance of 100 ms. [EN 301 549 7.1.2]
- [ ] Where the site transmits, converts or records such video, caption data is preserved, including presentation data such as position, colours and text style. [EN 301 549 7.1.3]
- [ ] Where the player controls how captions are presented, users can adapt their displayed characteristics to their needs, except for captions that are unmodifiable characters such as bitmap captions. [EN 301 549 7.1.4]
- [ ] The player has a mode that plays spoken subtitles when the content provides them. It does not have to generate them. [EN 301 549 7.1.5]
- [ ] The player lets the user select and play the available audio description on the default audio channel. Letting the user choose among several audio tracks is accepted where the video technology has no dedicated mechanism. [EN 301 549 7.2.1]
- [ ] Where audio description can be played, it stays synchronised with the audio and video. [EN 301 549 7.2.2]
- [ ] Where the site transmits, converts or records such video, audio description data is preserved. [EN 301 549 7.2.3]
- [ ] Where the primary purpose of the component is to play video and it controls captions, audio description and spoken subtitles, the user can turn the chosen one on and off with a single action, at the same level as the volume control. [EN 301 549 7.3]

### 3.7 Does the site offer real-time voice or video calls, voice mail or an interactive voice response?

Examples: a browser-based call with customer service, a video consultation, a web softphone. Clause 6 then applies, with many detailed requirements on real-time text, video quality and interoperability. Table ZA.1 lists 6.0.2 to 6.0.9, 6.1.1, 6.1.2, 6.2.1.1 to 6.2.10, 6.3, 6.4, 6.5.2 to 6.5.6, 6.7.1 and 6.7.2 [EN 301 549 Annex ZA]. Only the entry points are summarised here; a project in this situation has to work from clause 6 itself.

- [ ] Where the site allows real-time two-way voice communication, it also allows real-time text, and both can be used at the same time. [EN 301 549 6.2.1.1, 6.2.1.2]
- [ ] Where the site shows caller identification or similar identification, it is available as text and programmatically determinable. [EN 301 549 6.3]
- [ ] Where the site provides voice mail, an auto-attendant or an interactive voice response, users can get the information and complete the tasks without hearing or speech. [EN 301 549 6.4]
- [ ] Where voice calls include real-time video, the video meets the minimum resolution and frame rate of the clauses, audio and video stay synchronised, audio activity is shown by a real-time indicator, and all active participants are indicated, including people who sign. [EN 301 549 6.5.2, 6.5.3, 6.5.4, 6.5.5, 6.5.6]
- [ ] Where voice calls include real-time video, the service provides total conversation: voice, video and real-time text together. [EN 301 549 6.7.1]

Clause 13.1 (relay services) is in Table ZA.1 for ICT that is, or invokes, a relay service. It was not reviewed for this file.

### 3.8 Does the site provide information about a product or a service, or documentation?

- [ ] Where the site presents information about a product in digital form, that presentation conforms to clause 9 if it is web content and to clause 10 if it is a downloadable document. [EN 301 549 12.1]
- [ ] Where the site presents information about a service, support services included, the same applies. [EN 301 549 12.2]
- [ ] Where the site, or an official page of the provider, documents how to use the service, that documentation gives, directly or through links, the accessibility features of the service, how to use them and how to get support for them. [EN 301 549 12.3]

Clauses 12.4 and 12.5 concern electronic programme guides: the guide tells which programmes have captions, audio description, spoken subtitles or sign language interpretation, and this can be found without starting the programme [EN 301 549 12.4, 12.5].

## 4. Documents offered for download

Clause 10 applies to documents that are not web pages, including documents that a page offers for download without embedding them: PDF files, office documents, e-mails sent by the service [EN 301 549 10.0]. A document embedded in a page and rendered with it is covered by clause 9.

- Clause 10 follows the same numbering as clause 9: the requirement for success criterion x.y.z is clause 10.x.y.z, with void clauses keeping the alignment [EN 301 549 10.0].
- Documents protected by a signature, encryption, a password or a watermark are covered when they are presented to the user [EN 301 549 10.0].
- [ ] Where the site offers a document for download, the document meets the requirements of clause 10. [EN 301 549 10]
- [ ] Where the site offers a document for download, the document does not block or override the user's preference settings for documented platform accessibility features, unless essential. [EN 301 549 10.7]

Point left open, to state as such: the introduction to Table ZA.1 says the table applies to documents downloadable from web pages, and Annex A says clause 10 is a minimum requirement for both websites and mobile applications, but the table itself lists no clause 10 requirement; clause 10 appears only in Table ZA.2 (mobile applications) [EN 301 549 Annex A, Annex ZA]. This file does not settle the question. The cautious reading is to apply clause 10 to downloadable documents.

## 5. European Accessibility Act: what Annex ZB adds

Annex ZB relates the clauses of the standard to the requirements of Directive (EU) 2019/882. It is informative. It warns that a service can fall under several rows of several tables, and points to the tables of clause A.2 as the practical way to assess a given service [EN 301 549 Annex ZB].

Rows that concern a website, as read in Tables ZB.4 and ZB.5:

| Requirement of the Act (Annex I) | Clauses named by the standard |
|---|---|
| Websites and online applications of every covered service are perceivable, operable, understandable and robust | 4.2, 9, 11 |
| Electronic information needed to provide the service | 4.2, 12.2, and through it clause 9 for web content and clause 10 for documents |
| Support services give information on the accessibility of the service | 4.2, 11.5.2, 12.3, 13.1 |
| E-commerce: information on the accessibility of the products and services sold, when the responsible operator provides it | 4.2, 5.4, 12.1, 12.2, 12.3 |
| E-commerce: identification, security and payment functions delivered as part of the service | 4.2, 5 (especially 5.1), 9, 10, 11 |
| E-commerce and consumer banking: identification methods, electronic signatures and payment services | 4.2, 5 (especially 5.1 and 5.2), 9, 10, 11 |

Notes on this table:

- Clause 4.2 holds the functional performance statements (use without vision, with limited vision, without hearing, with limited manipulation, with limited cognition, and so on). The standard presents the requirements of clauses 5 to 13 as the testable criteria that correspond to them [EN 301 549 4.1].
- For the last row, Table ZB.5 writes "especially 4.2.12". No clause 4.2.12 was found in V4.1.1, where clause 4.2 ends at 4.2.11. The reference is not reproduced in the table above.
- Clause 5.1 concerns closed functionality, which a website normally does not have. Clause 11 concerns non-web software, mobile applications included.
- This project's reading for an e-commerce site, to be confirmed against the tables of clause A.2: clause 9 for every page, sections 2 and 3 of this file where their conditions are met, clause 10 for downloadable documents such as invoices and terms, and clause 12 for product and service information.

## 6. How conformance is tested

Annex C is normative. For each requirement it gives a test that is sufficient to determine conformance, numbered after the clause: the test for clause 9.7 is C.9.7 [EN 301 549 Annex C]. The tables of Annex ZA give, for each clause, the condition and the test to use.

- [ ] In an audit report, record for each conditional clause of section 3 whether its condition is met, and why. A clause whose condition is not met is not applicable; a clause that was not looked at is not tested. [best practice]

## 7. What this file does not cover

- Clauses 5.1 (closed functionality), 8 (hardware), 11 (non-web software and mobile applications) and 13 (relay and emergency services).
- The detailed requirements of clause 6.
- Any version of the standard other than V4.1.1.
- Annex B, which relates each requirement to the user needs of clause 4.2.
