# Module: file uploads

Load this module when users can send files to the site (avatar, CV, attachment, document, image for a listing). It completes [../web-baseline.md](../web-baseline.md). The accessible upload control itself is in [../../accessibility/components/file-upload.md](../../accessibility/components/file-upload.md).

## How to use this file

1. The ANSSI web guide has no section on uploads. The rules below come from the OWASP Top 10 categories and general practice; their tags say so. The few ANSSI rules that apply (content type, isolation of untrusted content) are tagged `ANSSI WEB`.
2. Uploaded files are untrusted input, like form fields, but heavier: they can carry scripts, malware, oversized payloads, or personal data the site then has to protect.
3. A static site cannot receive files itself. If a static site uses a third-party form service for uploads, these rules apply to that service: check its documentation and say so in the report.

## 1. Accept only what is expected

- [ ] The server keeps an allowlist of accepted types for each upload field (for example JPEG, PNG and WebP for an avatar; PDF for a CV) and rejects the rest [OWASP A06]
- [ ] The type is decided from the file's content (magic bytes, or by decoding it with an image library), not from the extension or the `Content-Type` sent by the browser, which the user controls [OWASP A06]
- [ ] A maximum size is enforced by the server and by any proxy in front of it, before the whole file is read into memory [OWASP A06]
- [ ] The number of files per request and per user over time is limited [OWASP A06]
- [ ] Images are re-encoded (decoded and saved again) by a maintained library, which drops embedded scripts and metadata such as GPS position [best practice]
- [ ] Archives (ZIP) are not unpacked unless needed; if they are, total unpacked size, number of entries and paths are checked [best practice]
- [ ] SVG uploads are refused, or sanitised and served as attachments: an SVG can contain script [best practice]

## 2. Store safely

- [ ] Uploaded files are stored outside the web root, or in object storage, never in a folder where the server executes code (PHP, CGI) [OWASP A06]
- [ ] Files are stored under a name generated by the server (random identifier); the original name is kept only as data, after cleaning [OWASP A01]
- [ ] The original name never reaches a file path: no `../`, no absolute path, no control characters [OWASP A01]
- [ ] Access to a stored file checks that the requester may see it; a hard-to-guess URL alone is not access control for private documents [OWASP A01]
- [ ] Files holding personal data have a retention period and are deleted with the account or the request they belong to [GDPR art. 32]
- [ ] Where the owner can run it, files are scanned by an antivirus before other users can download them [best practice]

## 3. Serve safely

- [ ] Uploaded files are served with the type decided by the server and `X-Content-Type-Options: nosniff`, so a file cannot be run as HTML or script [ANSSI WEB R6]
- [ ] Files other than images shown inline are served with `Content-Disposition: attachment` [best practice]
- [ ] User files are served from a separate domain (not a subdomain sharing cookies with the main site), so a malicious file cannot read the site's session [ANSSI WEB R27]
- [ ] User documents shown in the page (PDF preview, HTML from a converter) are displayed in a sandboxed iframe [ANSSI WEB R51]

## 4. In the report

Write the accepted types, the size limit, where files are stored, how access is checked, how long files are kept, and whether a malware scan is in place or left to the owner.
